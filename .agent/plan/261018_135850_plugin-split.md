# Plan — `plugin-split`: one plugin per topic, then the new plugins

## Context

The single `optimiziramsi-skills` plugin is all-or-nothing per project: the only way to drop a
concern is an env kill-switch. The user wants each project to pick its plugin set (enable only
what suits it, personalize the rest) and wants new concerns on top: a context-usage nudge with a
repack/refresh path, update-available and new-plugin nudges, a plugin that runs the updates and
refreshes for the user, and a skills-maintenance plugin.

Topic-first (0.0.2) already made every `<topic>/` folder plugin-shaped, so the split is mostly
mechanical. Platform facts it rests on (CC docs, checked 2026-10-18 against CLI 2.1.278):

- Per-project selection: `enabledPlugins` in the project's `.claude/settings.json`; install with
  `claude plugin install <p>@optimiziramsi --scope project`. A user opts out locally with
  `"<p>@optimiziramsi": false` in `.claude/settings.local.json`.
- A plugin is copied into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` alone —
  nothing outside its own dir exists at runtime (`../lib` is rejected). Symlinks to elsewhere in
  the marketplace are dereferenced for git sources but **skipped for a local-path marketplace**,
  which is how `develop` is field-tested here — so shared code must be real copies.
- `dependencies` in plugin.json (auto-installed with the dependent; a dependency cannot be
  disabled while a dependent is enabled). `${CLAUDE_PLUGIN_DATA}` is a per-plugin persistent dir.
- `userConfig` exists but is stored only in **user/managed** settings (`pluginConfigs`) — it can
  never be committed with a project. Project-shared values must stay `env` in settings.
- No hook input carries context usage; the transcript's `message.usage` does. A hook cannot run
  `/compact` / `/clear` — only nudge. `/reload-plugins` applies an update without a restart.
- `claude plugin list --json --available` lists installed vs marketplace plugins + versions.

## Scope

In: the split (phase 1), the config convention (phase 2), the new plugins (phases 3–5). Out: the
looper/grinder live test (still the user's, `.todo`), any change to what a skill or hook does.

## Approach — phase 1, the split

- **One plugin per topic folder, dir name = plugin name**: `commit flow git instructions patterns
  repo reporting review session setup worktree`, id `<name>@optimiziramsi`. Each gets
  `<name>/.claude-plugin/plugin.json` and uses the default component layout (`skills/ commands/
  agents/ hooks/hooks.json`), so the manifests carry no path arrays. The repo root becomes a
  marketplace only; `marketplace.json` lists every plugin with `source: "./<name>"`.
- **`optimiziramsi-skills` survives as a deprecated bundle** (`optimiziramsi-skills/`, manifest =
  name + `dependencies` on all eleven): existing installs keep resolving, but because a bundle pins
  its dependencies enabled, projects should move to per-plugin enables and drop it.
- **Shared code is vendored, not linked.** Root `lib/` stays the single source (`hookio.py`,
  `selftest.py`); `./vendor.sh` copies each module into every plugin that imports it
  (`<plugin>/lib/`), and `tests.sh` fails on drift. Hooks, bins and tests resolve `lib/` from their
  own plugin root (`parents[1]`), never the repo root. `flow`'s worktree confinement needs
  `worktree`'s guards + their suite at runtime, so `vendor.sh` also mirrors those into
  `flow/vendor/worktree/` — still one implementation, enforced byte-identical.
- **Per-plugin versions + per-plugin `CHANGELOG.md`.** All start at `0.1.0-dev.1`; the root
  `CHANGELOG.md` is frozen as pre-split history. `tests.sh` § 8 runs per plugin: a plugin whose
  shipped files changed must bump its own version. `release.sh` releases every plugin whose tree
  differs from `main`, requires a final version + a CHANGELOG section for each, tags
  `<plugin>--v<version>` (CC's dependency-resolution tag shape), and no longer auto-opens a dev
  series — a plugin's next edit forces its own bump.
- **Soft cross-plugin references stay soft.** Skills naming another plugin's skill (`/retro`,
  `/handoff`) degrade to a dead mention when that plugin is absent. No `dependencies` between the
  eleven — `flow` is self-sufficient via the vendored guards.
- **Runner pointer** moves to `<claude-config>/plugins/data/optimiziramsi-flow/current` → the flow
  plugin root (links: `…/current/bin/{loop,grind}`); `runner-link` re-aims existing repo links.

## Approach — later phases (detail planned when reached)

2. **Config convention** — project-shared values: `env` in `.claude/settings.json`; personal per
   project: `env` in `.claude/settings.local.json`; personal machine-wide: plugin `userConfig`
   (exported to hooks as `CLAUDE_PLUGIN_OPTION_<KEY>`). One resolver in `hookio`:
   env > plugin option > default. Each plugin's README lists its keys.
3. **`upkeep`** — SessionStart nudge (throttled, cached in `${CLAUDE_PLUGIN_DATA}`): enabled
   plugins with a newer marketplace version, and marketplace plugins this project hasn't seen yet;
   `/upkeep` skill runs marketplace update → plugin update → tells the user `/reload-plugins`.
4. **`context`** — hook reads the transcript's last `usage` and nudges at thresholds; `/repack`
   skill writes the handoff and hands the user `/clear` → `/continue` (or `/compact`). Spec (user,
   2026-10-18 — the new CCD UI dropped its context bar, so this is the only signal left):
   default thresholds **30% / 50% / 60% of a 1M window** (300k / 500k / 600k tokens), each
   configurable. 30% and 50% are light notes; at **60% the nudge is explicit that a handoff is
   needed** (write it, then `/clear` → `/continue`). The user can answer any nudge with an
   override that the plugin remembers for the session: "remind me later" (snooze — re-nudge after
   a further step), "keep going" (silence the current level), or "this topic is done" (the
   handoff is moot; offer `/clear`).
5. **skills maintenance** — scope open (below).

## Open questions

- Skills maintenance: a project's own `.claude/skills` (lint, trigger evals via `claude plugin

- Field-testing `develop` per project: keep "this checkout's branch is what every project loads",
  or add a second marketplace name (`optimiziramsi-dev`) a project opts into?
